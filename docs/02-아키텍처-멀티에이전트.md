# 멀티 에이전트 아키텍처

## 아키텍처 패턴: Thin Orchestrator + Specialized Agents

GSD의 핵심은 **얇은 오케스트레이터**가 **전문화된 에이전트**를 생성(spawn)하는 구조이다.
오케스트레이터는 컨텍스트의 30-40%만 사용하고, 각 에이전트는 독립된 신선한 컨텍스트에서 실행된다.

```
┌─────────────────────────────────────────────┐
│            Orchestrator (얇은 조율자)          │
│        컨텍스트 사용: ~30-40%                  │
│                                              │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│   │ Planner  │  │ Executor │  │ Verifier │  │
│   │ (계획자)  │  │ (실행자)  │  │ (검증자)  │  │
│   │ ~50%     │  │ ~50%     │  │ ~50%     │  │
│   └──────────┘  └──────────┘  └──────────┘  │
│                                              │
│   각 에이전트 = 독립 컨텍스트 (신선함 유지)      │
└─────────────────────────────────────────────┘
```

## 11개 전문 에이전트

### 핵심 에이전트 (Core Pipeline)

| 에이전트 | 역할 | 입력 | 출력 |
|----------|------|------|------|
| **gsd-planner** | 실행 가능한 단계별 계획 생성 | CONTEXT.md, ROADMAP.md | PLAN.md |
| **gsd-executor** | 계획을 코드로 구현, 작업별 커밋 | PLAN.md | SUMMARY.md, 커밋 |
| **gsd-verifier** | 목표 달성 여부 검증 | PLAN.md, SUMMARY.md, 코드 | VERIFICATION.md |

### 연구 에이전트 (Research)

| 에이전트 | 역할 | 입력 | 출력 |
|----------|------|------|------|
| **gsd-phase-researcher** | 계획 전 기술 조사 | CONTEXT.md | RESEARCH.md |
| **gsd-project-researcher** | 프로젝트 초기 도메인 조사 | 프로젝트 범위 | research 파일들 |
| **gsd-research-synthesizer** | 연구 결과를 실행 가능한 결론으로 | research 파일들 | 종합 리포트 |

### 품질 에이전트 (Quality)

| 에이전트 | 역할 | 입력 | 출력 |
|----------|------|------|------|
| **gsd-plan-checker** | 계획이 목표를 달성하는지 사전 검증 | PLAN.md | 승인/반려 |
| **gsd-integration-checker** | 컴포넌트 통합 검증 | 코드베이스 | 통합 리포트 |

### 유틸리티 에이전트 (Utility)

| 에이전트 | 역할 | 입력 | 출력 |
|----------|------|------|------|
| **gsd-codebase-mapper** | 기존 코드베이스 분석 | 코드베이스 | 분석 리포트 |
| **gsd-debugger** | 체계적 디버깅 | 에러 로그, 코드 | 수정 계획 |
| **gsd-roadmapper** | 요구사항으로부터 로드맵 생성 | REQUIREMENTS.md | ROADMAP.md |

## 모델 프로파일 시스템

에이전트마다 사용할 모델을 제어하는 3가지 프로파일:

```
┌──────────────┬─────────┬─────────┬─────────┐
│ 에이전트      │ quality │balanced │ budget  │
│              │ (고품질) │(균형)   │ (저비용) │
├──────────────┼─────────┼─────────┼─────────┤
│ planner      │ Opus    │ Opus    │ Sonnet  │
│ executor     │ Opus    │ Sonnet  │ Sonnet  │
│ verifier     │ Sonnet  │ Sonnet  │ Haiku   │
│ researcher   │ Opus    │ Sonnet  │ Haiku   │
│ plan-checker │ Sonnet  │ Sonnet  │ Haiku   │
│ debugger     │ Opus    │ Sonnet  │ Sonnet  │
│ roadmapper   │ Opus    │ Sonnet  │ Sonnet  │
└──────────────┴─────────┴─────────┴─────────┘
```

**선택 기준:**
- `quality`: 최고 품질, 높은 비용 (중요한 프로젝트)
- `balanced`: 기본값, 계획은 Opus/실행은 Sonnet (대부분의 프로젝트)
- `budget`: 저비용, 빠른 속도 (프로토타이핑, 단순 작업)

## 에이전트 파이프라인 (데이터 흐름)

```
[project-researcher] → .planning/research/STACK.md
        │
        ▼
[roadmapper] → ROADMAP.md
        │
        ▼
[phase-researcher] → RESEARCH.md
        │
        ▼
[planner] → PLAN.md (여러 개 가능)
        │
        ├── [plan-checker] → 승인/수정 요청
        │
        ▼
[executor] → SUMMARY.md + 커밋들
        │
        ▼
[verifier] → VERIFICATION.md
        │
        ├── Gap 발견 시 → 수정 PLAN.md 자동 생성
        │                    → [executor] 재실행
        │
        └── 통과 시 → 다음 phase로 진행
```

## 병렬화 전략

### Plan 레벨 병렬화 (에이전트 간)
- 독립적인 Plan은 동시에 여러 에이전트가 실행
- `depends_on` 선언으로 의존성 관리
- Wave(파동) 시스템: 의존성 없는 Plan을 같은 Wave에 배치

```yaml
# config.json
parallelization:
  enabled: true
  max_concurrent_agents: 3
  min_plans_for_parallel: 2
```

### Task 레벨 (에이전트 내부)
- 한 Plan 안의 Task는 순차 실행
- 컨텍스트 명확성 유지를 위해

## 에이전트 정의 파일 구조

각 에이전트는 `/agents/` 디렉토리에 마크다운 파일로 정의된다:

```markdown
# gsd-planner

## Role
실행 가능한 단계별 계획을 생성하는 에이전트

## Model Profile
quality: opus | balanced: opus | budget: sonnet

## Input
- CONTEXT.md: 사용자 결정 사항
- ROADMAP.md: 현재 phase 정보

## Instructions
(상세한 프롬프트 엔지니어링)

## Output Format
- PLAN.md with frontmatter
- 2-3 tasks per plan
- XML structured tasks
```

## 비슷한 시스템을 만들려면

1. **에이전트 정의를 마크다운으로**: 각 에이전트의 역할, 입출력, 프롬프트를 .md 파일로 정의
2. **오케스트레이터를 얇게**: 조율자는 상태 관리만, 실제 작업은 에이전트에게 위임
3. **파이프라인으로 연결**: 에이전트의 출력이 다음 에이전트의 입력이 되는 체인 구성
4. **모델 프로파일**: 작업 특성에 따라 다른 모델을 사용 (비용/품질 균형)
5. **컨텍스트 분리**: 각 에이전트가 독립된 컨텍스트에서 실행되도록 설계
