# 핵심 디자인 패턴

GSD에서 사용하는 주요 디자인 패턴들을 분석한다.
비슷한 시스템을 만들 때 이 패턴들을 참고하면 된다.

---

## 패턴 1: Agent Output → Next Agent Input (파이프라인)

에이전트의 출력 파일이 다음 에이전트의 입력이 되는 체인 패턴.

```
[researcher] ──출력──▶ RESEARCH.md
                            │
                         입력│
                            ▼
[planner] ────출력──▶ PLAN.md
                            │
                         입력│
                            ▼
[executor] ───출력──▶ SUMMARY.md + 코드
                            │
                         입력│
                            ▼
[verifier] ───출력──▶ VERIFICATION.md
```

**장점**: 느슨한 결합, 각 에이전트 독립적으로 테스트 가능, 중간 산출물 재사용 가능

**구현 핵심**:
- 각 산출물의 형식을 템플릿으로 표준화
- 에이전트는 입력 파일의 경로만 알면 됨
- 중간 산출물을 Git에 커밋하여 추적 가능

## 패턴 2: Locked Decisions (잠긴 결정)

사용자가 `/gsd:discuss-phase`에서 내린 결정은 CONTEXT.md에 "잠긴 결정"으로 기록된다.
이후 Planner는 이 결정을 **반드시** 따라야 하며, 대안을 제시할 수 없다.

```markdown
# CONTEXT.md

## Locked Decisions (잠금 - 변경 불가)
| 결정 | 이유 |
|------|------|
| PostgreSQL 사용 | ACID 트랜잭션 필요 |
| Tailwind CSS | 팀 합의 |

## Deferred Ideas (보류 - Plan에 포함 금지)
- Redis 캐싱 → v2에서 고려
- GraphQL → 현재는 REST로 충분

## Open for Discretion (재량)
- 파일 구조
- 네이밍 컨벤션
```

**왜 중요한가**: AI가 사용자 결정을 무시하고 "더 나은" 대안을 제시하는 것을 방지

## 패턴 3: Deviation Rules (이탈 규칙)

실행 중 계획에 없는 상황이 발생했을 때의 행동 규칙.

```
상황                      행동              예시
────────────────────────────────────────────────────
버그 발견 (RULE 1)        자동 수정         null 체크 누락
필수 기능 누락 (RULE 2)   자동 추가         에러 핸들링 없음
스텁 발견 (RULE 3)        자동 제거/구현     TODO 코멘트
비필수 개선 (RULE 4)      사용자 확인       리팩토링 기회
아키텍처 변경 (RULE 5)    에스컬레이션       DB 스키마 변경 필요
```

**왜 중요한가**: AI가 범위를 벗어나는 변경을 하거나, 필요한 수정을 놓치지 않도록 명확한 가이드라인 제공

## 패턴 4: Goal-Backward Verification (목표 역추적 검증)

Task 완료 여부가 아닌, **Phase 목표 달성 여부**를 역추적으로 검증.

```
전통적 검증 (Forward):
  Task 1 완료? ✓ → Task 2 완료? ✓ → Task 3 완료? ✓ → "Phase 완료!"
  문제: Task가 완료되어도 목표를 달성 못할 수 있음

GSD 검증 (Backward):
  Phase 목표: "사용자가 로그인할 수 있다"
    └── 로그인 페이지가 존재하는가? (EXISTS)
    └── 로그인 폼이 실제 구현되어 있는가? (SUBSTANTIVE)
    └── 폼 제출이 API에 연결되어 있는가? (WIRED)
    └── 실제로 로그인하면 대시보드로 이동하는가? (FUNCTIONAL)
```

**4단계 검증 레벨**:

| 레벨 | 이름 | 확인 사항 | 예시 |
|------|------|-----------|------|
| 1 | EXISTS | 파일/경로 존재 | `src/app/login/page.tsx` 있는가? |
| 2 | SUBSTANTIVE | 실제 내용 (스텁 아님) | `// TODO` 없는가? |
| 3 | WIRED | 시스템 연결 | 라우팅에 등록되어 있는가? |
| 4 | FUNCTIONAL | 실제 동작 | curl 또는 테스트 통과? |

## 패턴 5: Checkpoint System (체크포인트)

실행 흐름 중간에 인간의 판단이 필요한 지점을 명시적으로 선언.

```
자동 실행 ──▶ Task 1 ──▶ Task 2 ──▶ [CHECKPOINT] ──▶ Task 3 ──▶ ...
                                         │
                                    인간이 확인
                                    승인 후 재개
```

**3가지 체크포인트 유형**:

```xml
<!-- 90%: 시각적/기능적 확인 -->
<checkpoint type="human-verify">
  브라우저에서 /login 열고 로그인 테스트
</checkpoint>

<!-- 9%: 기술 선택/결정 -->
<checkpoint type="decision">
  A) JWT + 쿠키
  B) 세션 기반
  어떤 것을 선택?
</checkpoint>

<!-- 1%: 수동 작업 필요 -->
<checkpoint type="manual">
  AWS 콘솔에서 S3 버킷 생성 후 알려주세요
</checkpoint>
```

## 패턴 6: Decimal Phase Numbering (소수점 Phase 번호)

Phase 사이에 긴급한 작업을 삽입할 때 전체 번호를 다시 매기지 않는 방식.

```
원래:    Phase 1 → Phase 2 → Phase 3

삽입 후: Phase 1 → Phase 1.1 → Phase 1.2 → Phase 2 → Phase 3
                   ↑ 새로운     ↑ 새로운
                   삽입 Phase    삽입 Phase
```

**규칙**:
- `phase insert N` → Phase N 뒤에 N.1 생성
- 이미 N.1이 있으면 N.2 생성
- 제거 시 자동 번호 재조정
- 순서: 1, 1.1, 1.2, 2, 2.1, 3, ...

## 패턴 7: Context Window Management (컨텍스트 윈도우 관리)

```
┌────────────────────────────────────────────┐
│         Context Window = 200K tokens        │
│                                             │
│  목표: 각 에이전트가 50% 이내에서 작업 완료    │
│                                             │
│  전략:                                       │
│  1. Plan당 2-3 Task로 제한                   │
│  2. @file 참조 (인라인 복사 금지)              │
│  3. 에이전트별 독립 컨텍스트                    │
│  4. 오케스트레이터는 상태만 관리 (30%)          │
│  5. 결과물은 파일로 저장 (컨텍스트에서 제거)     │
└────────────────────────────────────────────┘
```

**안티 패턴 (하지 말 것)**:
- 하나의 대화에서 전체 프로젝트 구현
- Plan에 10개 이상의 Task 포함
- 에이전트에게 전체 코드베이스를 읽히기
- 이전 에이전트의 출력을 다음 에이전트에 인라인으로 전달

## 패턴 8: Template-Driven Output (템플릿 기반 출력)

모든 산출물은 미리 정의된 템플릿을 따른다.
AI가 자유 형식으로 쓰면 일관성이 없어지므로.

```markdown
# PLAN.md 템플릿

---
phase: {N}
plan: {M}
type: auto | tdd
wave: {W}
depends_on: []
---

## Objective
{1문장: 무엇을 왜}

## Context
{@file 참조 목록}

## Tasks
{XML 구조 Task 2-3개}

## Verification
{체크리스트}

## Output
{생성될 파일 목록}
```

**장점**: 파싱 가능, 일관된 품질, 검증 자동화

## 패턴 9: Async State Machine (비동기 상태 머신)

STATE.md가 Single Source of Truth 역할.
모든 워크플로우는 STATE.md를 먼저 읽고 작업을 시작한다.

```
워크플로우 시작
    │
    ▼
STATE.md 읽기 ──▶ 현재 위치 파악
    │               (Phase N, Plan M, Task K)
    │
    ▼
작업 수행
    │
    ▼
STATE.md 업데이트 ──▶ 새 위치 저장
    │
    ▼
다음 워크플로우가 STATE.md 읽고 이어서 진행
```

**세션 간 연속성**: 대화가 끝나도 STATE.md에 상태가 저장되어 있으므로,
새 세션에서 `/gsd:resume-work`로 정확한 중단 지점에서 재개 가능.

## 패턴 10: Verification-Driven Iteration (검증 기반 반복)

```
Plan 실행 → 검증 ──▶ 통과 → 다음 Phase
                 │
                 └──▶ 실패 (Gap 발견)
                         │
                         ▼
                 수정 Plan 자동 생성
                         │
                         ▼
                    수정 Plan 실행
                         │
                         ▼
                    재검증 (최적화됨)
                         │
                    ┌────┴────┐
                    │         │
                  통과      실패 → 반복
```

**최적화**: 재검증 시 이미 통과한 항목은 스킵하여 시간 절약
