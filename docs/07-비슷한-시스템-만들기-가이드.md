# 비슷한 시스템 만들기 가이드

## 이 문서의 목적

GSD와 비슷한 **AI 코딩 에이전트 오케스트레이션 시스템**을 직접 만들기 위한 실전 가이드이다.
핵심 개념과 구현 순서를 단계별로 설명한다.

---

## 1단계: 핵심 구조 이해

### 필요한 것들

```
나의-시스템/
├── agents/          ← AI 에이전트 프롬프트 정의
├── commands/        ← 사용자 명령어 인터페이스
├── workflows/       ← 오케스트레이션 로직
├── templates/       ← 문서 템플릿
├── references/      ← 참조 가이드
├── bin/
│   ├── install.js   ← 설치 스크립트
│   └── tools.js     ← CLI 상태 관리 도구
└── package.json
```

### GSD가 사용하는 핵심 패턴

| 패턴 | 설명 | 왜 필요한가 |
|------|------|-------------|
| Spec-Driven | 코드 전에 명세 작성 | AI가 명확한 목표 없이 코드를 쓰면 품질 저하 |
| Multi-Agent | 전문화된 에이전트 분리 | 컨텍스트 부패 방지, 각 에이전트가 신선한 상태 유지 |
| Atomic Commits | 작업 하나 = 커밋 하나 | 되돌리기 가능, 추적 가능 |
| Goal-Backward | 결과에서 역추적 검증 | AI가 "했다"고 하는 것을 신뢰하지 않음 |
| File-as-Database | 마크다운 = 데이터 저장소 | 외부 DB 불필요, Git으로 버전 관리 |

## 2단계: 에이전트 시스템 설계

### 최소 필수 에이전트 (3개)

비슷한 시스템을 만들 때 최소한 이 3개가 필요하다:

#### 1. Planner (계획 에이전트)
```markdown
# planner-agent.md

## Role
사용자의 요구사항을 실행 가능한 단계별 계획으로 변환

## Input
- 프로젝트 요구사항 (REQUIREMENTS.md)
- 현재 Phase 정보 (ROADMAP.md)
- 사용자 결정 사항 (CONTEXT.md)

## Output
- PLAN.md (2-3개 Task 포함)
- 각 Task에 name, files, action, verify, done 포함

## Instructions
1. 요구사항을 읽고 Phase 목표를 파악
2. 목표 달성에 필요한 최소 Task 도출
3. 각 Task를 독립적으로 실행 가능하게 정의
4. 검증 가능한 완료 조건 명시

## Constraints
- Task는 2-3개로 제한 (컨텍스트 절약)
- 각 Task는 하나의 커밋으로 완료 가능해야 함
- @file 참조로 컨텍스트 제공 (인라인 복사 금지)
```

#### 2. Executor (실행 에이전트)
```markdown
# executor-agent.md

## Role
PLAN.md의 Task를 순서대로 실행하고 원자적 커밋

## Input
- PLAN.md (실행 계획)

## Output
- 코드 변경사항 + 커밋
- SUMMARY.md (실행 결과)

## Instructions
1. PLAN.md에서 Task 읽기
2. <action> 지시에 따라 코드 구현
3. <verify> 지시로 동작 확인
4. <done> 조건 충족 확인
5. 원자적 커밋 생성
6. 다음 Task로 이동

## Deviation Rules
- 버그 발견: 자동 수정
- 필수 기능 누락: 자동 추가
- 비필수 변경: 사용자에게 물어봄
```

#### 3. Verifier (검증 에이전트)
```markdown
# verifier-agent.md

## Role
실행 결과가 Phase 목표를 달성했는지 검증

## Input
- PLAN.md (원래 계획)
- SUMMARY.md (실행 결과)
- 실제 코드베이스

## Output
- VERIFICATION.md (검증 결과)
- Gap 발견 시 수정 PLAN.md

## Instructions
1. Phase 목표 확인
2. 각 산출물에 대해 4단계 검증:
   - EXISTS: 파일이 존재하는가?
   - SUBSTANTIVE: 내용이 실제인가? (스텁 아닌가?)
   - WIRED: 시스템에 연결되어 있는가?
   - FUNCTIONAL: 실제로 작동하는가?
3. Gap 발견 시 수정 계획 자동 생성
```

### 선택적 추가 에이전트

필요에 따라 추가:
- **Researcher**: 기술 조사 (복잡한 도메인일 때)
- **Debugger**: 체계적 디버깅 (에러 처리 전문)
- **Codebase Mapper**: 기존 코드 분석 (브라운필드 프로젝트)

## 3단계: 상태 관리 시스템 구현

### 파일 기반 상태 관리

```javascript
// tools.js - 핵심 상태 관리 함수들

const fs = require('fs');
const path = require('path');

const PLANNING_DIR = '.planning';

// 상태 로드
function loadState() {
  const statePath = path.join(PLANNING_DIR, 'STATE.md');
  const content = fs.readFileSync(statePath, 'utf-8');
  return parseMarkdownState(content);
}

// 상태 업데이트
function updateState(field, value) {
  const state = loadState();
  state[field] = value;
  const markdown = renderStateMarkdown(state);
  fs.writeFileSync(path.join(PLANNING_DIR, 'STATE.md'), markdown);
}

// 설정 로드
function loadConfig() {
  const configPath = path.join(PLANNING_DIR, 'config.json');
  return JSON.parse(fs.readFileSync(configPath, 'utf-8'));
}

// Phase 정보 추출
function getPhase(n) {
  const roadmap = fs.readFileSync(
    path.join(PLANNING_DIR, 'ROADMAP.md'), 'utf-8'
  );
  return parsePhaseFromRoadmap(roadmap, n);
}

// 원자적 커밋
function atomicCommit(message, files) {
  execSync(`git add ${files.join(' ')}`);
  execSync(`git commit -m "${message}"`);
}
```

### 상태 머신 설계

```
프로젝트 상태 전이:

INIT → PLANNING → EXECUTING → VERIFYING → PHASE_COMPLETE
                                    │
                                    ├── Gap 있음 → RE_PLANNING → EXECUTING
                                    │
                                    └── 통과 → 다음 Phase 또는 MILESTONE_COMPLETE
```

## 4단계: 워크플로우 오케스트레이터 구현

### 핵심 워크플로우 흐름

```javascript
// workflows/plan-phase.js (의사 코드)

async function planPhase(phaseNumber) {
  const config = loadConfig();
  const roadmap = loadRoadmap();
  const phase = getPhase(phaseNumber);

  // Step 1: 연구 (선택적)
  if (config.workflow.research) {
    const research = await spawnAgent('phase-researcher', {
      input: { phase, roadmap },
      model: getModel('phase-researcher', config.profile)
    });
    saveFile(`phases/${phaseNumber}/RESEARCH.md`, research);
  }

  // Step 2: 계획 생성
  const plan = await spawnAgent('planner', {
    input: { phase, roadmap, context: loadContext(phaseNumber) },
    model: getModel('planner', config.profile)
  });
  saveFile(`phases/${phaseNumber}/PLAN-01.md`, plan);

  // Step 3: 계획 검증 (선택적)
  if (config.workflow.plan_check) {
    const check = await spawnAgent('plan-checker', {
      input: { plan, phase },
      model: getModel('plan-checker', config.profile)
    });

    if (!check.approved) {
      // 수정 후 재시도
      return planPhase(phaseNumber); // 재귀
    }
  }

  updateState('status', 'planned');
}
```

## 5단계: 컨텍스트 엔지니어링 적용

### 핵심 원칙

```
┌─────────────────────────────────────────────┐
│           Context Window (200K tokens)       │
│                                              │
│  ┌────────────────────┐                      │
│  │ Orchestrator ~30%  │ ← 얇게 유지          │
│  │ (상태 관리만)       │                      │
│  └────────────────────┘                      │
│                                              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │Agent ~50%│ │Agent ~50%│ │Agent ~50%│     │
│  │(독립)    │ │(독립)    │ │(독립)    │     │
│  └──────────┘ └──────────┘ └──────────┘    │
│       ↑ 각각 신선한 컨텍스트에서 시작          │
└─────────────────────────────────────────────┘
```

### 구현 팁

1. **@file 참조 사용**: 컨텍스트에 파일 내용을 직접 복사하지 말고 참조
   ```markdown
   ## Context
   @PROJECT.md
   @.planning/ROADMAP.md
   ```

2. **Plan당 Task 수 제한**: 2-3개 (많으면 컨텍스트 소모)

3. **에이전트 간 통신은 파일로**: 에이전트 A의 출력 파일 → 에이전트 B의 입력

4. **오케스트레이터는 읽기만**: 오케스트레이터가 코드를 직접 읽지 않고, 에이전트에게 위임

## 6단계: 검증 시스템 구현

### 4단계 검증 체크리스트

```javascript
function verifyArtifact(filePath, expectedBehavior) {
  const result = {
    exists: false,
    substantive: false,
    wired: false,
    functional: false
  };

  // Level 1: EXISTS
  result.exists = fs.existsSync(filePath);
  if (!result.exists) return result;

  // Level 2: SUBSTANTIVE (스텁 감지)
  const content = fs.readFileSync(filePath, 'utf-8');
  const stubPatterns = [
    /TODO/i, /FIXME/i, /PLACEHOLDER/i,
    /not yet implemented/i, /coming soon/i,
    /throw new Error\(['"]Not implemented/,
  ];
  result.substantive = !stubPatterns.some(p => p.test(content));

  // Level 3: WIRED (다른 파일에서 import/사용되는가)
  // grep으로 해당 모듈이 다른 곳에서 참조되는지 확인

  // Level 4: FUNCTIONAL (실제 실행 테스트)
  // 테스트 실행 또는 curl 등으로 확인

  return result;
}
```


## 핵심 교훈 & 설계 원칙

### 1. 에이전트는 마크다운으로 정의한다
코드가 아닌 프롬프트 엔지니어링이 핵심이다.
에이전트의 행동은 .md 파일의 Instructions 섹션에 의해 결정된다.

### 2. 상태는 파일 시스템에 저장한다
외부 DB가 필요 없다. Git으로 버전 관리까지 자동으로 된다.

### 3. 오케스트레이터는 최대한 얇게
오케스트레이터가 많은 일을 하면 컨텍스트가 빨리 차서 품질이 떨어진다.

### 4. 에이전트 간 통신은 파일로
에이전트 A의 출력 파일이 에이전트 B의 입력이 된다. 느슨한 결합.

### 5. AI의 "완료" 주장을 믿지 말라
반드시 Goal-Backward Verification으로 결과물을 독립적으로 검증한다.

### 6. 컨텍스트 사용량을 관리하라
Plan당 Task 수를 제한하고, 인라인 복사 대신 @file 참조를 사용한다.

### 7. Deviation Rules를 명시하라
예상치 못한 상황에서 에이전트가 어떻게 행동할지 미리 정의한다.
